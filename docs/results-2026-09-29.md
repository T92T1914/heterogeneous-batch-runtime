# CPU and CUDA execution results

I tested these workloads on an AMD Ryzen 7 7800X3D and NVIDIA RTX 4090, then kept the measurements that did not favor acceleration. The CUDA kernels completed correctly, but their complete calls were slower than the optimized CPU in every condition in this bounded comparison. A short kernel time did not remove allocation, validation, transfer and synchronization costs.

The baseline source is `675bd82ad9f2ed25cda41835835a1074ebc88ace`. The CPU dispatch follow-up is `b2cb6a8370646bb9a044ad677c8d4551bb8d1161`. Both protocols were committed before their respective measurements. The [execution receipt](evidence/execution.json) records source, binary and output hashes. All 504 timing rows remain available in the [baseline CPU](evidence/baseline-cpu.csv), [baseline CUDA](evidence/baseline-cuda.csv) and [follow-up CPU](evidence/followup-cpu.csv) files.

## Correctness and packaging

Windows verification used MSVC 19.44, Python 3.11 and CUDA compiler 13.4.59. Linux verification used Ubuntu 24.04.5 under WSL2, GCC 13.3 and Python 3.12. WSL is a Linux execution environment here. It is not a separate physical Linux host or evidence of Linux GPU execution.

The initial Windows receipt contains 14 passed steps. The Linux receipt contains 15. Checks cover Release builds, the native numerical and lifetime contract, portable operation with AVX2 disabled, installed CMake consumers, fresh Python wheels and 15 Python contract tests. Linux also executed AddressSanitizer and UndefinedBehaviorSanitizer with leak detection and immediate undefined-behavior failure. After the CPU dispatch correction, 12 Windows and 15 Linux steps passed again. These step counts are verification groups, not independent test-case counts.

Actual CUDA tests cover empty and partial shapes, finite reduction, nonfinite rejection, the conservative overflow guard, both histogram implementations and positive and negative maximum-finite stencil input. A separate application consumed the installed CPU and CUDA libraries and executed both. No implicit NumPy dtype conversion is accepted. The Python boundary snapshots input before releasing the GIL.

During development, the maximum-finite stencil test failed because the final rounded addition overflowed. Dividing each contribution by nine did not completely prevent that edge case. The corrected implementations bound the final mean to the finite input range, and the regression is retained. This behavior is part of the [numerical contract](contracts.md), not a claim that arbitrary cancellation has negligible error.

## Completed GPU work versus CPU

These are medians of five warm samples at 1024 by 1024 elements from the original comparison. The first invocation is retained separately in the CSV. It is not a cold-process measurement. All durations are milliseconds.

| Workload | Optimized CPU, two threads | CUDA complete call | CUDA kernel interval |
| --- | ---: | ---: | ---: |
| Masked reduction | 4.7211 | 6.9292 | 0.1570 |
| Stencil | 4.6808 | 5.2319 | 0.2577 |
| Histogram, uniform bytes, global bins | 0.3792 | 0.8524 | 0.1024 |
| Histogram, uniform bytes, shared bins | 0.3792 | 0.6562 | 0.0363 |
| Histogram, one occupied bin, global bins | 0.3020 | 0.7198 | 0.0541 |
| Histogram, one occupied bin, shared bins | 0.3020 | 0.8253 | 0.1385 |

Host timing uses the same outer boundary for every backend, including validation, result allocation, checksum selection and host result destruction. CUDA also completes transfers and synchronization and releases its operation resources before return. Device events separately bracket upload, kernels and download. Those intervals are not added to host elapsed time. The host buffers are pageable, and no transfer overlap is claimed.

The shared-bin experiment preserved exactly the same pixels, tile ownership and counts. At the largest uniform condition it reduced the observed kernel median. Under concentrated input it was slower. The evidence supports exposing the choice and retaining both results. It does not support claiming shared memory always improves a histogram.

The host was shared. No competing agent benchmark ran, but ordinary user applications remained active. GPU utilization was 21 percent before the measurement batch and 12 percent after it. Fixed condition order and only five warm samples limit inference. These values describe this run, not a hardware ranking or a promise for larger workloads. The separate CPU dispatch correction below does not retroactively change this baseline.

## A narrow CPU correction

The first results showed excessive small-stencil overhead. Inspection found that the optimized path queried CPU and OS AVX2 support for every output row. I moved that invariant decision before the row workers. The arithmetic, row implementation and partitioning remained unchanged.

| Square side | Threads | Original optimized stencil | Dispatch once per call |
| --- | ---: | ---: | ---: |
| 32 | 1 | 0.0421 | 0.0053 |
| 32 | 2 | 0.0988 | 0.0787 |
| 256 | 1 | 0.6048 | 0.2492 |
| 256 | 2 | 0.3916 | 0.2656 |
| 1024 | 1 | 6.8309 | 5.0436 |
| 1024 | 2 | 4.6499 | 4.0420 |

Every listed median decreased in the follow-up, with numerical tests still passing. Thread creation still outweighs useful work in small cases. The unchanged reduction and histogram rows remain in the follow-up as controls, including their timing variation. This is a useful local correction with bounded evidence, not a general speedup claim.

## Profiling and remaining diagnostics

Nsight Systems 2026.3.2 captured seven actual kernel launches, seven host-to-device copies and six device-to-host copies in a separate 256 by 256 profile run. The published [kernel summary](evidence/summary_cuda_gpu_kern_sum.csv), [API summary](evidence/summary_cuda_api_sum.csv) and [transfer summary](evidence/summary_cuda_gpu_mem_time_sum.csv) come from that trace. CPU sampling and context-switch tracing were disabled. Raw reports with local paths remain private.

The first stream creation occupied about 73.69 ms in that instrumented process. That startup observation is distinct from the warm measurements. Shared histogram kernels occupied most of the tiny profile's kernel time, including the concentrated input. Profiling overhead and its smaller input mean its durations should not replace benchmark samples.

Nsight Compute 2026.3.0 returned `ERR_NVGPUCTRPERM`. Hardware counters were not available to this account. Compute Sanitizer returned exit 99 with two initialization errors because the WDDM debugger interface was unavailable. The numerical test still completed, but this is not a sanitizer pass. No driver, debugger, security, clock, power or display setting was changed to remove either restriction. Device allocation failure and actual device-loss recovery were not injected or established.

The first hosted Windows wheel job also failed because its workflow forced Visual Studio 2022 while that runner had a different available generator. The correction reuses the generator from the successful native configuration. Hosted CI status is linked from the repository and must be checked at the revision being used. A local pass did not erase that failed job.

## Reproduce and interpret

Build and run CTest before measuring. Run `hbr_bench --run` for CPU or `hbr_cuda_bench --run` for CUDA, using the committed protocols and one measurement workload at a time. `hbr_cuda_bench --profile-case` provides the bounded profiler input. Configure CUDA for the actual compatible device. The tested device used architecture 89.

Run `python tools/validate_evidence.py` to check artifact hashes, complete condition groups, finite timings and cross-backend checksums in the retained output. These checks supplement the numerical tests. A checksum is not a substitute for comparing full outputs.

The public source is independently authored. No private application code, captured inputs, toolkit binaries or fonts are included. This phase does not establish AMD GPU behavior, cross-vendor equivalence, a universal workload crossover or a production deployment. The CPU remains the default Python path, and optional real execution is demonstrated separately in [Adaptive Timing](https://github.com/T92T1914/adaptive-timing-engine/blob/main/docs/real-execution.md).
