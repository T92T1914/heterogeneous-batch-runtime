# Batching decision protocol

Declared before deciding collection on October 14, 2026. The study uses a permitted bounded Runtime GPU/performance slot. Preserve ordinary shared-machine activity and record it as a limitation. Do not infer an idle machine from that slot grant. One owned operation at a time, one compiler/BLAS/inference thread and a bounded owned Windows Job. CPU/build work uses 512 MiB committed memory. Required-CUDA initialization was qualified separately after the 512 MiB cap caused a DLL allocation failure and a 1 GiB diagnostic allowance failed at provider setup. The admitted CUDA limit is 2 GiB aggregate committed memory in the owned Job. At that bound the original serial session initialized with a measured process private-commit peak of 1,103,470,592 bytes, and all 25 separately installed required-CUDA correctness cases passed. This is a host process bound, separate from device memory and the existing arena option. The final bound is fixed before deciding collection. No system paging-file, driver or account setting changes. No old benchmark is repeated.

Decision: determine whether genuine batch execution adds correct multi-image capability and improves completed request throughput at batches 2 and 8 in the existing consumer. Correct capability is accepted independently of speed. A modest timing difference is inconclusive when its paired variation spans zero. Preserve every slower and failed case.

Models: original pinned model and the narrowly derived batch graph. All weights/operators/preprocessing remain identical. Record original and execution graph hashes and the exact shape recipe. This is a combined graph/execution change, not an attribution of every timing difference to a wrapper or GPU kernel.

Conditions: serial and batched modes on CPU and cuda-required, at N=1,2,8. Same original geometric images, per-image preprocessing and complete owned host logits. CPU and CUDA use the same ONNX Runtime version, sequential graph optimizations, one intra/inter-op thread and the existing required-provider contract. CUDA cannot fall back. Preserve TF32 disabled and existing arena configuration, which is not a total GPU memory bound.

Primary boundary: start before preparing the original in-memory uint8 images, submit through the existing InferenceExecutor/OwnerExecutor, and stop only after wait/reconciliation yields the completed usable owned result. This includes preparation, the consumer snapshot, admission, queueing, synchronous native inference, output materialization and result adoption. It excludes file reading/PNG decoding and is not file-to-result latency. Independent complete-logit validation follows each result outside the timed interval and has its own duration. Retain executor observation times to qualify queueing and execution boundaries without adding overlapping intervals to the total.

Secondary boundary: direct prepared tensor Session.run through completed host output, including native input snapshot and output construction. Report this separately if collected. It does not replace the primary request cost or prove the cost of a device-resident chain.

Setup: session/graph construction duration and first request retained separately. Retirement: close duration and completed owner retirement recorded separately. There is one outstanding request and one owner session at a time. Do not compare many serial processes against one reused batch resource.

Order and counts: three predeclared paired blocks per batch/provider, declared before deciding collection. Rotate the batch order (1,2,8), (2,8,1), (8,1,2) across blocks. Serial-first versus batched-first is chosen by the parity of block plus the batch's fixed index in (1,2,8). This ensures every batch, including eight images, observes both mode orders. An initial block-plus-rotated-position rule was corrected during independent source review before collection. No observations used that rule. Each mode uses one reused owner session for its separately retained first request, five warmup requests and twenty deciding requests, then closes before the other mode starts. Pair requests by the same block and sample index. They are nonadjacent within a block, not alternating requests through two simultaneously active sessions. There are sixty deciding samples per mode/batch/provider but only three block replications. Each session admits twenty-six fresh deterministic request identities within the existing 256-identity limit. CPU and required CUDA are separate serial collector operations with sixty seconds each. The global deciding budget is 120 seconds including setup/retirement. The collector CLI defaults to 120 seconds for one provider, and the declared two-provider invocation uses --max-seconds 60 on each. Stop visibly on any mismatch, required-provider error, timeout or missing owner retirement. Do not tune or discard negative conditions.

Output: retain all ten logits per image, original-reference max difference and tolerance result. Compare against original serial ReferenceEvaluator outputs at rtol=1e-5, atol=2e-5. Actual one-model-invocation evidence and actual CUDA placement belong to correctness acceptance, not timing inference. No change to tolerance merely to make a result pass.

Analysis: publish median, range, p95, throughput in images/second, all sixty samples per condition, each block median and within-block range/p95, and same-index request differences. Use a fixed-seed bootstrap interval of the three paired block median differences, not an interval treating every within-block request as an independent replication. The statistic is the median of serial block median minus batched block median. Positive favors batched. Use 2,000 bootstrap replicates and seed 10414 plus the batch size. The interval is the linear-interpolated 2.5th/97.5th percentile and is coarse with only three blocks. An interval spanning zero is inconclusive. Label this small shared-workstation study and retain every slower condition. It does not establish fleet performance or a universal crossover point. No gain is promised.

Memory: record Windows working set/private committed/cumulative peak process values before setup, after setup, after requests and after close, with phase identity. Observe device memory at separately stated boundaries through existing permitted tools, preserving other-device-use and sampling limits. Report process counters as process counters, not allocation ledgers, leaks or hard ceilings. The 128 MiB arena setting is separate. Do not collect privileged counters or change driver/security/display settings.

The original reports and negative CUDA comparisons remain byte-preserved at their own revisions. New rows and qualification belong to the new source, not a relabeling of historical evidence.
