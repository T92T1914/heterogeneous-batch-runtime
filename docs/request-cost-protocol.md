# Goal C prospective diagnostic protocol, October 15, 2026

The actual baseline is merged PR19 at 9fcc2ecc7bed1f0bc84a3aca33212f619bef40e0. The diagnostic is bounded to five minutes total serialized diagnostic/correctness/comparison operations, one owner/thread, 512 MiB aggregate committed host memory for CPU and 2 GiB for CUDA. No installation, system-setting change or profiler enforcement bypass is authorized. All operations use the existing owned Windows Job runner and original separately installed consumers. The diagnostic source and this declaration are frozen before collection.

Existing evidence was analyzed first. At N8 batched, same-request mean caller intervals are CPU preparation15.867us, admission44.148us, wait315.720us, gap1.378us and total377.113us; CUDA preparation15.720us, admission42.680us, wait661.402us, gap1.335us and total721.137us. The gap is Dispatch/timer work between preparation and admission, not a transfer remainder. Worker execution may overlap admission. Retained coarse executor observation deltas do not resolve submillisecond native/worker costs.

Question: how much of the existing N8 batched completed host request is contained in the worker's synchronous Session.run envelope, and how much observer disturbance accompanies a same-host-clock probe or ordinary ORT host profiling? No serial-versus-batched campaign is repeated. No device kernel, transfer or synchronization cost will be inferred from unexplained intervals. The installed traces currently show host Node/Session categories and no Kernel categories; profiler build-flag support remains unconfirmed.

Conditions: installed CPU and required-CUDA environments, explicit batched N8, unchanged original/derived graph identities, original provider/thread/precision policy and complete independently owned host float32(8,10) outputs. Three conditions are plain unprofiled consumer, two-timestamp worker envelope, and existing native ORT profiling. Three independent fresh processes/sessions per condition/provider. Rotate condition order (plain,worker,ort), (worker,ort,plain), (ort,plain,worker) by replicate; serialize providers. Each session has one first request, five warmups and twenty recorded samples. Only three process replications are available. No p99/SLO/capacity claim or calibrated population confidence.

Input frames are the same original eight geometric images, their horizontal reflections, a fixed duplicate/permuted row order, and seeded uint8 images with seed10415. Rotate frames each request. Fixture construction and reference evaluation are outside primary timing. Each request receives a freshly supplied uint8 array and includes prepare_arrays owned snapshot/normalization, submission, all required native/provider copying/execution and usable completed host-result reconciliation. File/PNG decoding remains excluded. Compare every score against original serial ONNX ReferenceEvaluator at rtol1e-5 and atol2e-5; retain all values and failures. No cached result, pre-uploaded tensor or device-resident output replaces work.

The diagnostic reuses compare_batching's Budget, serialization, installed identity inventory and process-memory helper plus the existing InferenceExecutor. It introduces no resource owner or serving framework. Caller phase timestamps and the optional worker envelope use time.perf_counter_ns, qualified with time.get_clock_info. Worker entry/return encloses Python Session.run validation, native input snapshot, synchronous ORT work, output construction and final checks. Prefix+worker+suffix are a same-request nonoverlapping host partition. Worker entry may precede admission return. Executor monotonic observations, Dispatch virtual times and ORT session-relative microseconds remain separate clock domains; no cross-clock subtraction is performed.

Plain runs provide an unprofiled diagnostic control with the same common caller timers, validation and journaling. Differences estimate additional worker/ORT observer disturbance, not all instrumentation overhead relative to an observer-free production request. Worker/ORT conditions are instrumented diagnostics and cannot supply an optimization speed claim. Report each process median/range and all samples, plus paired process-median perturbation plain versus instrumented; report signs and mixed results without discarding adverse observations. Setup/first requests, validation/log retention and close remain separate. Process counters include references/libraries/report state and do not isolate allocations or device memory. Ordinary ORT Node events, including names ending kernel_time, are not counted as CUDA kernels. Trace files are retained separately. The internal collection clock includes source/reference setup, row journaling and retirement, ending before final JSON serialization; the enclosing process limit also covers model loading and final output serialization.

At most18 diagnostic operations, each with an8-second internal collection clock and10-second enclosing process limit, plus two20-second correctness qualifications. The220second sum of process caps alone is not a total-budget guarantee. The reused Job runner now has an optional300second aggregate wall guard: it accounts for startup, hashing, output and cleanup in actual elapsed time, reserves the full next operation plus five-second cleanup before starting, and stops rather than starting a case without that remaining allowance. It records aggregate elapsed time and preserves its earlier source before this small guard addition. Model acquisition is not repeated. No failed operation is assigned a completed latency. A setup, provider, output, identity or retirement failure stops the admitted sequence and is preserved. Do not enlarge caps or retry until favorable. Owned cleanup is a resource safeguard, not a performance result. After a late request failure, close may physically finish and reconcile a result: retain that result with successful retirement while leaving the request/study incomplete.

Correctness qualification additionally exercises both modes for every N0..8, changing/reordered/duplicate rows, unaligned contiguous input and retained independent outputs against the original reference. Existing targeted cancellation, staleness, failed invocation, thread and close contracts remain acceptance; native/package behavior is unchanged by the diagnostic. Required CUDA must actually execute under this grant; a CPU stand-in does not satisfy it.

Optimization admission: select at most one Runtime-local mechanism only if a measured component and a compatible concrete change support a prospective N8 completed-request benefit of at least5percent and10microseconds. Preparation alone is below5percent of retained N8 cost even under an optimistic complete-removal bound. The broad Session.run envelope cannot alone justify I/O binding or removing validation/ownership. A no-change/inconclusive conclusion is acceptable when a specific change lacks that evidence; missing device instrumentation remains explicitly unobserved. Any later candidate needs a separately frozen unprofiled baseline/candidate protocol within the remaining grant, all N0..8/lifetime acceptance and an actual separately installed affected package. No candidate is promised by these diagnostics.
